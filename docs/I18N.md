# komponist – Internationalisation (i18n)

How the UI texts are stored, generated and used. Background and the decisions behind it:
the i18n evaluation (internal notes) (§14 holds the owner's decisions of 2026-11-15). Languages today: German (source)
and English.

## 1. How it works

`crates/komponist-i18n` is a leaf crate. Its `build.rs` reads `locales/<lang>/*.ftl` (Project Fluent syntax) and
generates the Rust API at build time:

```text
crates/komponist-i18n/
  locales/de/<area>.ftl     German, the source language (verbatim from the screens, CLAUDE.md rule 1)
  locales/en/<area>.ftl     English: the same keys and the same variables
  generator.rs              the generator (used by build.rs and by the golden tests)
  build.rs                  reads the folders, writes $OUT_DIR/catalog.rs, stops the build on errors
  src/lib.rs                Count, Plural, the plural rule of each language, Lang::from_code
  tests/it/                 golden tests of the generator, tests of the generated API
  tests/fixtures/locales/   a small catalog the tests compile to try plurals, variables and terms
```

Generated (`komponist_i18n::`):

| Item | Meaning |
|---|---|
| `Lang` | `Copy` enum, one variant per folder (`De`, `En`); `Lang::default()` is `De`; `Lang::ALL`, `code()`, `from_code("de_DE.UTF-8")` |
| `t.dock_devices()` | static text: `&'static str` |
| `t.status_clips_selected(n)` | text with variables or plurals: `String`; a selector variable is `impl Count`, any other `impl Display` |
| `Lang::by_id("undo-duplicate-clips")` | `Option<&'static str>` for a stored message id (undo labels); static messages only |
| `de::DOCK_DEVICES`, `en::DOCK_DEVICES` | the static texts as constants, for tests and `match` patterns |

Rustdoc of every method shows the `.ftl` comment and the German and English text, so hover in the editor tells
what a message is.

### Use in code

```rust
// A view (komponist-app): ViewCtx carries the language.
let t = cx.lang;
w::Button::new(t.dock_maximize()).show(ui);
node.set_label(t.a11y_clip(&clip.name, first, last));          // text with variables: String

// A widget that owns texts (komponist-ui): the language lives in the egui Context.
let t = komponist_ui::lang(ui.ctx());

// A test: German is the default and the test language.
h.get_by_role_and_label(Role::Button, de::DOCK_COLLAPSE);        // static texts
assert_eq!(Lang::De.status_clips_selected(2), "2 Clips ausgewählt");
```

`App::new` always starts in German and never reads the environment. `main()` resolves the language
(`settings::startup_lang`: `--lang de|en`, else `Settings.language`: `system`, `de` or `en`, an unknown value counts as
`system`; `system` is German on a German desktop and English otherwise, read with `sys-locale`) and calls
`App::with_lang`. Each frame the app writes the language into the egui `Context` (`komponist_ui::set_lang`), so tests
in one binary do not share it, and into the AccessKit root node (`set_language`, BCP 47 code).

**Language switch (#5):** Settings › Darstellung has the row Sprache (System / Deutsch / English), the action
`SettingsAction::SetLanguage`. It sets `App::lang`, clears the status message (it is text of the old language), saves
`settings.json` and asks for another frame, so every text changes in the next frame without a restart. `--lang` only
decides the language of one run: a choice in Settings wins from then on and is saved, the next start with `--lang`
uses the flag again. The names of the three segments are the same in every language (Deutsch, English).

## 2. Files and keys

- One file per area, so parallel work touches different files: `shell` (panel titles, resize edges, empty dock
  bodies), `transport` (transport bar and its menu), `status` (status bar and every `App::set_status` text),
  `record`, `project-io` (new/open/save messages and file error reasons), `undo` (undo step labels), `keys`,
  `dialog`, `start`, `settings`, `file`, `new-project`, `new-track`, `missing`, `export`, `plugin-frame`, `format`,
  `a11y`, `builtin`, `dock` (pilot), `ui` (widgets, timeline names `a11y-*`, graph texts of `komponist-ui`).
  The dialogs (#3) have one file each: `dialog` (what they share: ×, Cancel, "Master", "Spur …", months, relative
  times, latency), `start`, `settings`, `file`, `new-project` (also the unsaved prompt and the default names),
  `new-track`, `missing`, `export` (also the status texts of an export) and `plugin-frame` (header, body, the
  "GUI cannot be opened" status).
  The views (#2) have one file per area: `arrangement`, `piano-roll`, `step-seq`, `browser`, `devices` (cards,
  add-device menu, sidechain chip and popover, preset menu), `mixer`, `inspector`, `routing` (the routing UI of
  `views/routing`, used by mixer, arrangement and inspector), plus `view-common` (texts several views share: grid,
  snap and zoom buttons, grid entries, the "late" indicator, the track hue names) and `undo-views` (the undo labels
  the views send that `undo.ftl` did not have).
  A key belongs to exactly one file for all languages and the whole crate: a second `undo-change-row` in another
  area file is a duplicate-key build error, so look in the existing files first.
- **Keys** are kebab-case, `<area>-<name>`: `dock-no-clip`, `file-open-title`. They become `dock_no_clip()` and
  `de::DOCK_NO_CLIP`. Do not name a key like a Rust keyword (`type`) or like a `Lang` method (`code`, `plural`,
  `by-id`); the build says so.
- A key exists once, in every language, in the file of the same name. Variables are the same in every language.
- Every message has a `#` comment with its design source (`S09 recent header`, `Designsystem tab`). Group
  headers use `##`.
- Variable names are snake-friendly (`$clip_name` or `$name`); the parameter order of the method is the order of
  first appearance in the **German** text.

### Status messages and undo labels

- **Status messages** (`App::set_status`) are `String`s in the current language, formatted when the event happens
  (`self.lang.status_midi_connected(name)`). They are transient; a language switch clears them.
- **Undo labels are message ids** (the i18n evaluation (internal notes) §7.7, decided in WP-73). The model keeps the label of an
  undo step as an opaque `String` and stays free of texts. The app passes the id when it applies an edit or begins a
  gesture (`self.apply("undo-quantize", …)`, `EditAction::BeginGesture { label: "undo-tempo".into() }`) and resolves it
  only where it shows a label: `undo_label::text(lang, label)`, `App::undo_text()` and `App::redo_text()`. A switch
  relabels the steps already made. The id must be a **static** message of `undo.ftl` (`Lang::by_id`).
- A label with a name in it (a plugin parameter) carries the name after U+001F: `undo_label::param(name)`,
  `device_param(plugin)`, `plugin_state(plugin)` build `undo-param␟Cutoff`; `text` calls `undo_param(name)`. A new
  label with variables needs a case in `undo_label::text`.
- Anything that is not an id shows as it is: take names (content). Since #2 every view sends ids (`undo-track-height`,
  `undo-volume`, `undo-set-note`, `undo-change-row`, …); a view that needs a label `undo.ftl` lacks adds it to
  `undo-views.ftl`. Tests compare `app.undo_text().as_deref()` with the German text (or the raw id in a
  `BeginGesture { label }`); a test in `undo_label.rs` fails when a `"undo-…"` literal in the sources has no message.
- Undo labels are Title Case in English ("Move Notes"): they are menu items ("Undo Move Notes").

### Views (issue #2)

- A view reads its texts as `ctx.lang.area_name()` (`ViewCtx::lang`). A function without a `ViewCtx` but with a `Ui`
  reads `komponist_ui::lang(ui.ctx())` once at its start (never inside `widget_info`, see the pitfall below); a
  pure model function gets a `lang: Lang` parameter (`routing::output_targets(lang, …)`, `mixer::model::strips(lang, …)`,
  `inspector::model::take_rows(lang, …)`, `devices::model::failure_texts(lang, …)`). The old `names` modules of the views
  are gone; tests use the generated `de::AREA_NAME` constants and `Lang::De.area_name(…)`.
- **Ids are not texts.** The browser's folder keys (`effects/eq-filter`, `project/takes`) and egui ids are language
  independent, so a language switch keeps folders open and closed.
- **Texts built from parts** are whole messages with variables (`routing-send-on`, `step-seq-step-on`); a text select
  (`{ $tap -> [pre] … *[post] … }`) takes the part that differs (`"pre"`/`"post"`). Fragments that are appended
  (`step-seq-step-probability`, `, probability 50%`) keep their leading comma in the message.
- **Units** (`st`, `%`, `BPM`, `kHz`) stay Rust constants (`inspector::model::units`); they are values and notation.
- Track hue names are `hue-*` (`views::hue_name(lang, i)`, `views::hue_swatches(lang)`): the UI crate's
  `track_swatches()` carries German names for the gallery only.
- Sampler and wave names that come from the built-in devices (`Sinus`, parameter names, pad names) are
  **plugin-provided text** (§5) and belong to the built-in devices' own work package (#4).

## 3. Add a message

1. Add it to `locales/de/<area>.ftl` with a `#` comment: the German text, verbatim from the screens.
2. Add the same key and variables to `locales/en/<area>.ftl` (style guide, §6). The build fails otherwise.
3. Use it: `t.area_name()`. Run `cargo check -p komponist-i18n` to see the generator's errors first; they name
   file and line.

### The supported Fluent subset

| Construct | Example | Note |
|---|---|---|
| text | `dock-mixer = Mixer` | multi-line values work as in Fluent |
| variable | `greeting = Hallo { $name }` | values are formatted in Rust (`fmt_db`, `fmt_pos`, …) and passed in |
| string literal | `braces = { "{" }Text{ "}" }` | for `{`, `}` and leading or trailing spaces |
| term | `{ -komponist }` | plain text only, substituted at build time; define it in each language that uses it |
| plural select | `{ $n -> [0] Keine *[other] { $n } }` | selector is a variable (`impl Count`); keys are integers or CLDR categories (`zero`, `one`, `two`, `few`, `many`); `*[other]` is required and the only default |
| text select | `{ $state -> [on] an *[off] aus }` | selector is a variable (`impl AsRef<str>`); keys are identifiers that are not plural categories, no number keys; exactly one default (any key). Every language must have the same keys and the same default |

Errors (all with file and line): key missing in a language, key only outside German, different variables, select
without `*[other]`, anything else (attributes, message references, functions such as `NUMBER()`, number literals,
number keys in a text select, a variable used as number and as text selector, terms with variables or arguments), syntax errors, duplicate keys, keys that clash with a
Rust keyword or a `Lang` method.

Typography lints are build errors too (on the final text of every message, terms and literals included):

- ASCII `...` in any language: write U+2026.
- `en` only: `„` (U+201E; English quotes are “…”, U+201C and U+201D, which are fine) and the word "Strg".
- An ASCII hyphen-minus that acts as a minus sign, directly before a digit and not after a letter or digit
  (` -3 dB`, `(-12 dB)`): write U+2212. Compounds and ranges such as `24-Bit` or `1-4` pass, because a letter or digit
  stands before the hyphen; ranges should still use the en dash (`1–4`) in new texts, but the lint does not enforce it.

Plurals are selects, never `if n == 1` in Rust:

```ftl
status-clips-selected =
    { $n ->
        [one] 1 Clip ausgewählt
       *[other] { $n } Clips ausgewählt
    }
```

## 4. Add a language

1. Create `locales/<code>/` (lower-case code: `fr`, `pt-br`) and copy every `.ftl` file of `de/`. `cargo build -p
   komponist-i18n` lists everything still to translate.
2. **Plural rule.** `Lang::plural` in `crates/komponist-i18n/src/lib.rs` is a `match` over all languages; the build
   fails with "non-exhaustive patterns" until the new language has an arm. That arm is the only code a language needs:
   - one, other (German, English, Spanish, Italian, …): `Plural::germanic(n)`;
   - others: write the CLDR rule (https://unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html),
     for example Polish `n == 1 → One`, `n % 10 in 2..=4 && n % 100 not in 12..=14 → Few`, rest `Many`/`Other`; or call
     `icu_plurals` (ICU4X, Unicode licence) and map its categories to `Plural`. The generator already emits arms for
     `[zero] [one] [two] [few] [many]`, so no generator change is needed.
3. Add the language to `Language` in `komponist-app/src/settings.rs` (the settings enum, `resolve`), to `LANGUAGES`
   of the row in S07 "Darstellung" (`dialogs/settings.rs`, with a `settings-language-<code>` message in every
   language: the name of the language in that language). `--lang <code>` and the system language pick it up
   through `Lang::from_code`.
4. Check the fonts: IBM Plex covers Latin, Cyrillic and Greek; CJK, Arabic, Hebrew, Devanagari and Thai need more
   (the i18n evaluation (internal notes) §7.10). Right-to-left needs bidi support in egui first.

## 5. What not to translate

- **Names:** komponist, hexa, klopfer; plugin names and vendors; CLAP, VST3, MIDI; PipeWire, JACK, ALSA; device
  and port names from the system.
- **User content:** project, track, clip, take, step-row and pattern names, file names, paths. Default names
  ("Unbenannt", "Take 3", "Pattern 2") are made in the current language when they are created and are content
  afterwards, saved in the project and never retranslated. The demo project "Night Drive" is content, and it is English in every UI language (like the factory preset names): nothing translates it.
- **Plugin-provided text** (foreign CLAP and VST3 plugins): parameter names, value texts, preset names, plugin log
  lines. The built-in devices' own texts are not plugin text: they are catalog texts (§8); only their preset *names*
  are never translated.
- **Values and notation:** note names are **C D E F G A B** everywhere (no German H), C4 = 60; positions (10.2.120),
  times (00:17.902), dB, pan (C, L 12, R 50), decimal point and U+2212 minus, units (dB, dBFS, Hz, kHz, ms, s, BPM),
  key letters and digits in shortcuts. These are formatters in Rust, passed into messages as arguments.
- **Developer-facing text:** log lines, CLI usage and errors, internal `Display` texts, egui ids, test-plugin names.
  English code, commits and docs stay English.
- **The gallery** (`komponist-gallery`) keeps literal German; it mirrors the design system page.
- **English terms in the German design are still catalog texts** (identical in `en`): Piano Roll, Step Sequencer,
  Mixer, Inspector, Browser, Loop, Snap, Velocity, Swing, Ratchet, Take, Bypass, Solo, Mute, Record-Arm, Monitoring.

## 6. Style guide

### German (source)

Verbatim from `Screens.dc.html`, including typography: „…“ quotes, U+2212 minus, " · " separators, en dash in
ranges, "…" after a space for actions that need more input ("Projekt öffnen …"), "35 %" with a space, keys as
"Strg Shift E", time "heute 09:12". The DAW is **komponist**, not "klang-studio".

### English (US)

| Topic | Rule |
|---|---|
| Spelling | US English: Color, Center, Canceled, Gray |
| Capitalisation | **Title Case** for titles, buttons, tabs, menu items and dialog headings ("Open Project…", "No Clip"); **sentence case** for labels, tooltips, accessible names of icon-only buttons, status texts and hints ("Collapse dock", "No track armed") |
| Quotes | “curly” (U+201C … U+201D) around names; never „ in `en` |
| Ellipsis | U+2026 without a space before it, for actions that need more input: "Open Project…" |
| Percent | "35%" (no space) |
| Time | 24-hour: "today 09:12", "yesterday", "5 minutes ago", "Oct 12", "Oct 12, 2025" |
| Shortcuts | "Ctrl+Shift+E", "Space", "Del", "Backspace", "Home", "End"; letters, digits, arrows, `+`, `−`, `[`, `]`, `,` as they are |
| Ranges | en dash: "Bars 1–4" |
| Values and units | unchanged: "−3.2 dB", "120 BPM"; the space before the unit stays |
| Wording | short, active, imperative on buttons ("Save", "Export…"), no "please", no exclamation marks |
| Never | ASCII `...`, ASCII hyphen as a minus before digits |

Shell, status and undo texts (WP-73): the status bar's context hints write mouse modifiers as "Ctrl+drag", "Alt+click"
(German "Strg-Ziehen", "Alt-Klick"); hints are sentence case, separated by " · ". A project file's failure reason is one
message per cause (`project-reason-*`, lower case after the colon); the system's own error text goes to the log only.
A plural in German that is not grammatical in the source ("1 von 1 Noten") stays as the screens have it: the German
select has the same text in every branch, English has the grammatical plural.

Group fold is "Collapse" / "Expand" everywhere, also in the undo label ("Collapse or Expand Group"). "Alt+click" has a
plus in every hint and tooltip. A short key text that must fit a toolbar field gets its own message next to the full
accessible name (`step-seq-length-key` "Len." beside `step-seq-length` "Length"); look at the English snapshots
(`*-en-1x.png` in `crates/komponist-app/tests/snapshots`, one per main screen) when you change an English text, and
shorten the text, not the layout.

Keyboard names (`KeyChord::label`, WP-72): Strg → Ctrl, Leertaste → Space, Entf → Del, Rücktaste → Backspace,
Pos1 / Ende → Home / End; German separates with a space, English with "+".

macOS shortcuts (#47, owner decision 4): the shortcut modifier is ⌘, and labels are glyphs in Apple's order without a
separator in **both** languages ("⌘S", "⇧⌘Z", "⌥+"; `KeyChord::label_on(t, Platform::Mac)`; messages `key-command-mac`,
`key-shift-mac`, `key-alt-mac`, `key-separator-mac`). A text that names the shortcut modifier in prose has a second
message with the suffix `-mac` ("Strg T: MIDI-Spur" → `status-empty-hint-mac` "⌘T: MIDI-Spur"); the code picks with
`Platform::current().pick(pc, mac)`. Alt stays "Alt" in prose hints on both platforms. The glyphs come from the bundled
`KomponistKeys` font (`assets/fonts/README.md`): egui panics on a glyph no font has, so a new symbol needs a glyph first.
The native macOS app menu (`app-menu-*`) is one ordinary message per item, German "Einstellungen …", English "Settings…".

### Dialogs, dates and plurals (#3)

- A dialog is a pure view; `show` reads the language with `komponist_ui::lang(ctx)` (never inside a `widget_info`
  closure, see the pitfall below) and passes `t` down. Models and helpers that make texts take the language as the
  **first** argument: `start::recent_row(t, …)`, `ProjectSummary::meta(t)`, `missing_plugins::model(t, …)`,
  `settings::scan_summary(t, …)`, `format::relative_date(t, …)`, `FileBrowser::new(lang, …)` (the browser keeps the
  language for its messages and follows the UI's each frame). The `names` modules of the dialogs are gone; tests use
  `de::START_NEW`, `en::EXPORT_TITLE` and so on. Two notation marks stay in code: `header::names::NO_PRESET` ("—")
  and `CHANGED` (" *").
- Dates: months are `dialog-month-1` … `-12` (German "Okt.", English "Oct"); `dialog-date` / `dialog-date-year`
  order day, month and year as the language does ("12. Okt. 2025", "Oct 12, 2025"); times are always 24 h
  ("heute 09:12", "today 09:12"). Relative times are plurals (`dialog-minutes-ago`: "vor 5 Minuten", "5 minutes ago").
- Default content names are made in the current language when they are created: `new-project-default-name`
  ("Unbenannt", "Untitled") and `new-project-template-name` ("Beat-Skizze", "Beat Sketch"); the track and clip names of
  the template (Drums, Bass, Keys, Beat) are the same in both languages and stay literals.
- `missing::title_for(t, plugins, samples)` is the dialog title and the `$problems` of `project-opened-problems`
  (status bar), so the status shows Title Case in English ("Night opened · 2 Plugins Missing").
- What still comes from outside the catalogs: the plugin frame body's crashed card (`views::devices::model::failure_texts`,
  the device cards' work package) and the system's own error text in `file-unreadable`, `export-failed` and
  `export-open-failed` (`$reason`, `$why`; they are developer-facing causes, see §2).
- English format chip of built-in devices in dialogs: `missing-format-builtin` ("BUILT-IN"; German "INTERN"). `views::format_tag(lang, format)`
  is the one place for the chip text, so the device cards, browser, add menu and dialogs agree.

## 7. For volunteer translators

You need a text editor, the repository and a Rust toolchain; no Rust knowledge.

1. Copy the folder of an existing language that is complete (`crates/komponist-i18n/locales/en`) or start from
   `de`, and edit the `.ftl` files. One message is `key = text`; the line above it (`# …`) says where the text
   appears. Keep the key and every `{ $variable }` exactly as in German; change only the words around them.
2. Keep `{ … }` pairs closed. For counts, write one variant per plural form your language needs
   (`[one]`, `[few]`, `[many]`, `*[other]`; see the CLDR link above); `*[other]` stays last and marked with `*`.
3. Follow the style guide for your language; do not translate §5's names and values.
4. Run `cargo build -p komponist-i18n`. A missing key, a changed variable or a syntax error stops the build and
   names the file and line. Fix it and build again; `cargo test -p komponist-i18n` runs the generator's tests.
5. Start komponist with `scripts/run.sh --lang <code>` to see the result.

A new language also needs its plural rule in `src/lib.rs` (§4); ask a developer if you are unsure. A translation
platform (Weblate or Pontoon) follows when the repository is public; `.ftl` stays the source format.

## 8. Built-in devices and default names (#4)

The built-in devices (`komponist-builtin`) and the model's default names write their texts per language. The model
stays free of texts and of `komponist-i18n` (ARCHITECTURE §4): it takes the words as arguments. `komponist-builtin`
depends on `komponist-i18n` (a leaf crate), so a device builds its own texts.

### Catalog files

| File | Keys | Content |
|---|---|---|
| `device-names` | `device-name-<device>` | The name of each built-in device on the browser, the card and in messages |
| `defaults` | `default-name-<what>` | The words of default content names: `MIDI`, `Drums`, `Bus`, `Gruppe`/`Group`, the hi-hat rows |
| `params` | `value-*`, `param-*`, `choice-*`, `page-*`, `label-*`, `graph-title-*` | Value words, parameter names (shared ones as `param-<name>`, device ones as `param-<device>-<name>`), enum choices, page names, the name above a choice switch, graph titles |
| `presets` | `preset-category-<name>` | Preset category names (see below) |

A name followed by a number or a context placeholder takes it as a variable (`param-eq-band-freq` = "Frequency { $n }",
`graph-title-hexa-amp` = "Op { $op } · Amplitude", where `$op` is the placeholder text `{env_op}`).

### What the API looks like

| Need | Function | Note |
|---|---|---|
| Shown name of a built-in device | `komponist_builtin::device_name(lang, &plugin_ref)`, `Internal::name_in(lang)`, `Macro::name_in(lang)` | `PluginRef::name` is stored in the project and stays German ("Hall"); the UI looks the name up from the id |
| Parameters of an internal device | `Internal::params_in(lang)` | Cached per language; ids, kinds, ranges and defaults are the same in every language |
| Layout (pages, titles, choice labels) | `Internal::layout_in(lang)` | |
| hexa's card | `device::params_in(lang)`, `device::param_in(lang, id)`, `device::layout_in(lang)`, `Field::info_in(lang)`, `Macro::param_info_in(lang)`, `Macro::text_in(lang, v)` | |
| Value words | `komponist_builtin::value_texts(lang)` → `ParamInfo::texts(…)` | `On`/`Off` and the percent suffix; `params_in` sets them on every parameter. A bridged plugin's parameters get them from the plugin frame |
| Category name | `komponist_builtin::category_text(lang, category)` | Categories are stored as their German name (`hexa_core::categories`, `Preset::category`); an unknown one passes through |
| Default names | `komponist_model::edits::{add_track_in, add_bus_in}(…, &DefaultNames)`, `dialogs::new_track::default_names(lang)` | `add_track` and `add_bus` keep writing German |
| Default step rows | `step_rows::rows_for_in(lang, …)`, `step_rows::default_rows(lang)` | |

The functions without `_in` (`Internal::params()`, `device::layout()`, `Macro::name()`, `rows_for`, `add_track`) are the
German ones. Code that shows no text (wire ids, defaults, state, the engine) uses them; anything a user reads takes the
`_in` variant. A custom value text (`ParamInfo::formatted`) is a closure that captures the words of one language
(`let off = t.value_off(); info.formatted(move |v| …)`).

### Decisions

- **Preset names are English in every language** and are not in the catalogs (owner, 2026-11-15): one name per factory
  preset, the same in the German and the English UI. A device state stores the loaded preset's name (`"preset"`), so a
  rename needs an entry in `internal::preset_names` (old German name → new English name); `Internal::loaded_preset`
  resolves it, and a test loads a state with every old name. hexa's state is its patch and stores no name. New
  presets are named like other synths do: "Fat Saw", "Wide Pad", "Dotted Eighths"; compounds are written with a space
  ("Neuro Bass"), a hyphen stays where it is part of the word ("Lo-Fi Piano", "8-Bit Bass", "Hi-Hat", "E-Piano").
- **Preset categories are UI grouping** and translated (`preset-category-*`). They keep their German name as the
  stable id in `hexa-core` and in the devices' presets; only the shown text is looked up.
- **Device names:** brands stay (hexa, volt, presse, Sampler); generic names translate: Hall → **Reverb**,
  Tonleiter → **Scale**; EQ, Delay, Limiter and Arpeggiator are the same word.
- **Parameter labels** are short, 1–2 words, Title Case like the German loan words they sit next to ("Low Cut",
  "Key Scale", "Note Value"); a switch that reads as a sentence is sentence case ("Pad follows input"). Numbered
  parameters take the number last ("Frequency 2", "Level 3").
- **Units** are notation and stay: Hz, kHz, ms, s, dB, st, ct, `1/8T`, note names C D E F G A B. Two words change: percent
  is "40 %" in German and "40%" in English (`value-percent`), and volt's octave unit is "Okt." / "oct". "Aus" / "Off",
  "Frei" / "Free" and "Ende" / "End" are catalog words.
- **EQ band types** are LC, LS, Bell, HS, HC in English (German "Gl." for „Glocke“).
- **Default content names** (`MIDI 2`, `Bus 1`, `Gruppe 1`/`Group 1`, `Closed Hat`) are made in the current language when the
  track, bus, group or clip is created and are content afterwards. The template's `Drums`, `Bass`, `Keys`, `Beat` are the same
  in both languages and stay literals; the test kit's sample names and the demo's step rows (`Closed Hat`, `Open Hat`) are English content (file names) and stay.
- A German catalog text that must equal a constant of the code (the model's wave and source lists, the scale
  names) is checked by a test (`i18n::tests::the_german_lists_are_the_constants_the_code_always_had`), so the German UI
  cannot drift.

### Add a device or a parameter

1. Give the `Spec` `params: fn(Lang) -> Vec<ParamInfo>` and `layout: fn(Lang) -> DeviceLayout`; write every name as
   `t.param_…()` (shared concepts first: look for `param-mix`, `param-release` …).
2. A name for the browser: `device-name-<device>` in `device-names.ftl`, and an arm in `Internal::name_in`.
3. Presets are English literals; a rename later goes into `preset_names`.
4. The language-independence test (`language_changes_texts_never_ids_kinds_ranges_or_defaults`) covers the new device
   as soon as it is in `Internal::ALL`.

## Pitfall: reading the language inside `widget_info`

`Response::widget_info(|| …)` runs its closure while egui holds the context lock. Calling
`komponist_ui::lang(ui.ctx())` (or anything else that locks the context) inside it deadlocks; WP-72's
first gate hung 246 app tests this way. Read the language once before the closure:
`let t = komponist_ui::lang(ui.ctx()); resp.widget_info(|| WidgetInfo::labeled(role, true, t.…));`
